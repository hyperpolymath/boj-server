= BoJ Server — Extensibility Guide

== Purpose

This document describes how external developers can extend the BoJ catalogue
*without modifying core infrastructure*.  The extension mechanism exists to
make the design readily expansible; it is not a scope increase for the
project itself.

== The Capability Matrix

> The capability matrix, lifecycle, proof requirements, HAT model, and cartridge
> manifest schema are specified normatively in
> link:specification/cartridges/README.adoc[`docs/specification/cartridges/README.adoc`].
> This document covers the optional *backend (third axis)* extension mechanism only.

BoJ organises server capabilities as a sparse matrix:

[source]
----
               Protocol (column)
             ┌─────┬─────┬─────┬─────┬─────┬─────┐
  Domain     │ MCP │ LSP │ DAP │ BSP │ gRPC│ REST│
  (row)      ├─────┼─────┼─────┼─────┼─────┼─────┤
  Database   │  ██ │     │     │     │  ██ │  ██ │
  Container  │  ██ │     │     │     │  ██ │  ██ │
  ...        │     │     │     │     │     │     │
             └─────┴─────┴─────┴─────┴─────┴─────┘
----

*Two primary dimensions:*
* *Rows* = capability domains (database, container, secrets, k8s, ...)
* *Columns* = protocol types (MCP, LSP, DAP, BSP, gRPC, REST, ...)

*One optional third dimension:*
* *Depth* = backend/provider (universal, postgresql, podman, aws, ...)

== The Third Axis: Backend

Every catalogue entry has a `backend` label that defaults to `"universal"`
(the `backend` field of the `Cartridge` record in `src/abi/Boj/Catalogue.idr`,
set by `boj_catalogue_register` in `ffi/zig/src/catalogue.zig`).
Core BoJ cartridges are all universal — they define the capability
abstraction without committing to a specific provider.

NOTE: The label lives in the catalogue (Idris2 ABI and Zig FFI), not in
`cartridge.json`. The manifest schema (`schemas/cartridge-v1.json`) has no
`backend` property, so a backend is set at registration time with
`boj_catalogue_set_backend` (see <<register-ffi>>).

Community extensions can *specialise* this axis.  For example:

[cols="1,1,1,1",options="header"]
|===
| Cartridge
| Domain
| Backend
| What it does

| database-mcp
| Database
| universal
| Generic database operations

| database-pg-mcp
| Database
| postgresql
| PostgreSQL-native operations

| database-sqlite-mcp
| Database
| sqlite
| SQLite-native operations

| container-mcp
| Container
| universal
| Generic container operations

| container-podman-mcp
| Container
| podman
| Podman-specific tooling

|===

This means the matrix is actually:

[source]
----
  (Domain, Protocol, Backend) → Cartridge
----

But the third axis is opt-in.  If you don't set `backend`, it is `"universal"`
and the cartridge behaves exactly as the existing 2D model.

== Creating an Extension

To extend BoJ with a backend-specific cartridge:

=== 1. Write the Cartridge Manifest

> *Manifest format note:* the cartridge specification
> (link:specification/cartridges/README.adoc[§6, Cartridge Manifest (Nickel)])
> names *Nickel* (`.ncl`) as the authoritative manifest format; migration is pending. The
> manifests read today are `cartridge.json`. The Elixir catalog
> (`elixir/lib/boj_rest/catalog.ex`) validates each one against the bundled
> schema mirror `schemas/cartridge-v1.json` (see `schemas/SCHEMA-MIRROR.adoc`)
> and rejects a manifest that fails it.

Create a `cartridge.json` for your extension. Start from
`templates/cartridge-template/cartridge.json`. The name must end in its role
suffix (`-mcp`, `-lsp`, `-dap`, …), so a PostgreSQL specialisation of
`database-mcp` is `database-pg-mcp`, not `database-mcp-pg`. Community
extensions are always the `Ayo` tier. This example validates against
`schemas/cartridge-v1.json`:

[source,json]
----
{
  "$schema": "https://hyperpolymath.dev/standards/cartridges/cartridge-v1.json",
  "spdx": "MPL-2.0",
  "copyright": "Copyright (c) 2026 Your Name",
  "name": "database-pg-mcp",
  "version": "0.1.0",
  "description": "PostgreSQL-native database cartridge for BoJ",
  "domain": "Database",
  "category": "domain",
  "tier": "Ayo",
  "protocols": ["MCP", "REST"],
  "auth": {
    "method": "none",
    "env_var": null,
    "credential_source": null
  },
  "api": {
    "base_url": "local://database-pg-mcp",
    "content_type": "application/json"
  },
  "tools": [
    {
      "name": "pg_query",
      "description": "Run a read-only SQL query.",
      "inputSchema": {
        "type": "object",
        "properties": {
          "query": { "type": "string", "description": "SQL query string" }
        },
        "required": ["query"]
      }
    }
  ]
}
----

=== 2. Build the Cartridge Library

A cartridge is three layers: an *Idris2* ABI (the verified contract), a *Zig*
FFI and a *Zig* adapter. The FFI compiles to a shared library (`.so`, or
`.dylib` on macOS) that exports the five C-ABI symbols of ADR-0006
(`docs/decisions/0006-cartridge-invoke-abi.adoc`). This is the shape of
`templates/cartridge-template/ffi/cartridge_ffi.zig`, built with that
directory's `build.zig`:

[source,zig]
----
const shim = @import("cartridge_shim.zig");

export fn boj_cartridge_init() callconv(.c) c_int {
    return 0;
}

export fn boj_cartridge_deinit() callconv(.c) void {}

export fn boj_cartridge_name() callconv(.c) [*:0]const u8 {
    return "database-pg-mcp";
}

export fn boj_cartridge_version() callconv(.c) [*:0]const u8 {
    return "0.1.0";
}

// Return codes are frozen by ADR-0006: 0 success, -1 unknown tool,
// -2 bad arguments, -3 buffer too small (*in_out_len set to the size needed).
export fn boj_cartridge_invoke(
    tool_name: [*c]const u8,
    json_args: [*c]const u8,
    out_buf: [*c]u8,
    in_out_len: [*c]usize,
) callconv(.c) i32 {
    _ = json_args;
    if (shim.invokeArgsNull(tool_name, out_buf, in_out_len)) return shim.RC_BAD_ARGS;
    const body: []const u8 = if (shim.toolIs(tool_name, "pg_query"))
        "{\"result\":{}}"
    else
        return shim.RC_UNKNOWN_TOOL;
    return shim.writeResult(out_buf, in_out_len, body);
}
----

`cartridge_shim.zig` is `ffi/zig/src/cartridge_shim.zig`. Cartridges
themselves live in the `boj-server-cartridges` repository; its
`cartridges/templates/gossamer-mcp/` is the minting template, and its
`cartridges/domains/config/k9iser-mcp/adapter/` is the reference unified Zig
adapter.

=== 3. Submit via the REST API

The submission endpoint is specified in `docs/specification/openapi.yaml`
(`POST /community/submit`, body `CommunitySubmission`), and
`config/gateway-policy-boj.yaml` exposes it only to authenticated callers.

IMPORTANT: The Elixir REST server (`elixir/lib/boj_rest/router.ex`) does not
serve this route yet; a request falls through to its `route-not-found` 404.
The review state machine itself is implemented in `ffi/zig/src/community.zig`.

Once the route is served, a submission looks like this, with `BOJ_URL` the
node's REST endpoint (see `.env.example`):

[source,bash]
----
curl -X POST "$BOJ_URL/community/submit" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "database-pg-mcp",
    "author": "Your Name <you@example.com>",
    "repository": "https://github.com/you/database-pg-mcp"
  }'
----

The node operator reviews the submission through the Ayo-tier review state
machine in `ffi/zig/src/community.zig`
(submitted → under_review → approved / rejected, or suspended).

[[register-ffi]]
=== 4. Register Programmatically (FFI)

If you link against the BoJ catalogue library, call the C ABI that
`ffi/zig/src/catalogue.zig` exports. From Zig:

[source,zig]
----
extern fn boj_catalogue_init() c_int;
extern fn boj_catalogue_register(
    name_ptr: [*]const u8,
    name_len: usize,
    version_ptr: [*]const u8,
    version_len: usize,
    status: c_int, // BOJ_STATUS_*: 1 = ready
    tier: c_int, // BOJ_TIER_*: 2 = ayo
    domain: c_int, // BOJ_DOMAIN_*: 3 = database
) c_int;
extern fn boj_catalogue_set_backend(backend_ptr: [*]const u8, backend_len: usize) c_int;
extern fn boj_catalogue_add_protocol(protocol: c_int) c_int;

fn registerPg() bool {
    if (boj_catalogue_init() != 0) return false;
    const name = "database-pg-mcp";
    const version = "0.1.0";
    const backend = "postgresql";
    if (boj_catalogue_register(name.ptr, name.len, version.ptr, version.len, 1, 2, 3) != 0) return false;
    if (boj_catalogue_set_backend(backend.ptr, backend.len) != 0) return false;
    if (boj_catalogue_add_protocol(1) != 0) return false; // BOJ_PROTO_MCP
    return boj_catalogue_add_protocol(9) == 0; // BOJ_PROTO_REST
}
----

The constant values are those in `generated/abi/boj_catalogue.h`.

== What This Is Not

This extensibility mechanism is *not*:

* A plugin system with dynamic loading (extensions are static .so files)
* A marketplace or registry (BoJ does not host or distribute extensions)
* A scope increase (core BoJ cartridges stay universal)
* A commitment to support arbitrary backends

It is simply a *designed seam* in the type system that allows the
community to specialise the catalogue along a natural axis without
forking or modifying core infrastructure.  Someone can look at this
and say: "great, this is expansible" — and try out their own ideas
on the backend dimension.

== Querying Extensions

The catalogue's menu JSON, written by `boj_menu_json` in
`ffi/zig/src/catalogue.zig`, carries each entry's `backend` label:

[source,json]
----
{
  "menu": "teranga",
  "version": "0.1.0",
  "cartridges": [
    {
      "name": "database-mcp",
      "version": "0.1.0",
      "tier": "teranga",
      "status": "ready",
      "backend": "universal",
      "available": true,
      "protocols": ["mcp", "rest"]
    },
    {
      "name": "database-pg-mcp",
      "version": "0.1.0",
      "tier": "ayo",
      "status": "ready",
      "backend": "postgresql",
      "available": true,
      "protocols": ["mcp", "rest"]
    }
  ]
}
----

To read one entry's label, call `boj_menu_backend` (below). In the Idris2 ABI,
`byBackend` filters a list of cartridges by label.

NOTE: The REST surface does not expose the backend label yet. `GET /menu` in
`elixir/lib/boj_rest/router.ex` groups manifests by tier with no `backend`
field, and `GET /cartridges` returns only the cartridge names and a count; it
takes no `domain` or `backend` query parameters.

== Idris2 ABI

The `Cartridge` record in `Boj.Catalogue` includes:

[source,idris]
----
record Cartridge where
  constructor MkCartridge
  name       : String
  version    : String
  status     : CartridgeStatus
  tier       : MenuTier
  domain     : CapabilityDomain
  protocols  : List ProtocolType
  binaryHash : String
  backend    : String    -- "universal" | provider-specific label
----

Query functions:

[source,idris]
----
isBackendSpecific : Cartridge -> Bool
byBackend : String -> List Cartridge -> List Cartridge
----

== Zig FFI

The two backend exports of `ffi/zig/src/catalogue.zig`, as a caller declares
them:

[source,zig]
----
// Set the backend label (at most 32 bytes) of the last registered cartridge.
// The label is "universal" until this is called. Returns 0, or -1 on error.
extern fn boj_catalogue_set_backend(backend_ptr: [*]const u8, backend_len: usize) c_int;

// Copy the backend label of the cartridge at `index` into out_ptr.
// Returns the number of bytes copied, or 0 on error.
extern fn boj_menu_backend(index: usize, out_ptr: [*]u8, out_len: usize) usize;
----
